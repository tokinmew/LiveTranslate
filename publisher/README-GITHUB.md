# LiveTranslate public release publisher

This owner tool publishes a stable Windows update to **tokinmew/LiveTranslate**. It uses the existing GitHub CLI sign-in, Git for Windows and the Python runtime supplied with LiveTranslate. Publishing happens on your PC. It requires no GitHub Actions runner, hosted server or paid API. The local GitHub CLI session must have write access and be signed in to github.com as **tokinmew**. Keep the application source bundle one directory above the publisher scripts.

## Publish the supplied signed feed

1. Extract the publisher ZIP. Open **Publish GitHub release.cmd**. If asked, choose the release folder's **latest.json** and then **python.exe** inside your prepared LiveTranslate app's **runtime** folder.
2. The console prints the version, SHA-256 and size of each release asset. Choose **Yes** to publish to the dedicated public repository. If it does not exist and the GitHub account can create it, the publisher creates it with public visibility. An existing private repository is rejected; this tool never changes a repository's visibility.
3. The publisher verifies the signed manifest and checks every update file against the corresponding file under **LiveTranslate/** in the bundle's exact Git tag. An empty public repository receives the release commit on **main** and the original tag in one atomic push. An established repository receives only the matching tag and its source history. An existing **main** stays in place, and a different existing release tag stops publication.
4. The publisher uploads the numbered package and **latest.json** to a draft and reads each asset back by its GitHub ID. After verifying the bytes and remote source tag it publishes the stable release, then verifies the latest stable endpoint. The app checks **https://github.com/tokinmew/LiveTranslate** only. Readers download public releases without GitHub sign-in or GitHub CLI. A source push alone does not deliver an app update: the signed assets must be published as a stable GitHub release.

After an interruption, run the same publisher with the same signed bytes. It checks the draft, reuses matching assets and uploads missing assets. A changed asset or an incomplete previously published release stops publication. Use a new version for changed release contents. GitHub Actions and third-party update services are outside this release path.

## Prepare a future version

Generate the versioned application package and **latest.json** with **publish_update.py** from the LiveTranslate release tools. These files are publishing inputs; they are not an alternate in-app update source. Use your dedicated release signing key and **Sign-Release.ps1** to authorize that manifest. Keep the key in its owner-only location. Commit the corresponding editable app source under **LiveTranslate/**, tag the verified release commit, then make a complete bundle with **main** and that tag. For example, run `git bundle create LiveTranslate-source.bundle refs/heads/main refs/tags/vX.Y.Z` with the new version's tag. Include only sources and history suitable for public distribution. The public verification key can travel with the app; signing keys and credentials cannot.

With the app's bundled Python, pass **--feed PATH --dry-run** to **github_publish.py** for an offline preview. Add **--source-bundle BUNDLE** to select another bundle. The default is **../LiveTranslate-source.bundle**, relative to the publisher script directory. Use **--feed PATH --publish** to publish into the existing public repo. Adding **--init-public** explicitly allows creation of the dedicated public repo when missing. The old **--init-private** option is rejected. Git obtains publisher credentials from the existing GitHub CLI session for the fixed github.com HTTPS destination.
